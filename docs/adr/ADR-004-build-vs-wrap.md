# ADR-004 · 005 / 006 的自建 vs 封装成熟开源

**状态**: 接受
**日期**: 2026-08-13（提议）／2026-08-13（决策层接受）
**决策方**: longyuanai 设计/审计层
**关联派活**: `docs/dispatches/013-REV-GHIDRA.md`（005 轨）；006 轨待排
**前置门禁**: `011-INJECT-HARDEN` 审计 PASS；`012-STRUCT-DEBT` 已解锁但不依赖本 ADR

---

## 背景

2026-08-12 的架构审查读取了六个产品的实际实现，结论是：**LLM 的位置放对了**（确定性
解析器产出证据、LLM 做评估），确定性底座也是真的 —— 004 有 tree-sitter 五语言 +
taint/dataflow，005 有 capstone/pefile/pyelftools，006 有真实的 binwalk CLI 封装与
Docker/QEMU 用户态仿真。

但两个产品正在与成熟开源霸主平行造轮子：

| 产品 | 现状 | 对标 |
|---|---|---|
| 005 | `decompiler.py` 自述为"small evidence-preserving pseudo-C decompiler"，实际是线性反汇编之上的伪 C 生成 | [Ghidra](https://github.com/NationalSecurityAgency/ghidra)：NSA 开源、IR 级真反编译、headless 批处理 |
| 006 | binwalk 封装 + QEMU 仿真 + CVE 匹配 | [EMBA](https://github.com/e-m-b-a/emba)：提取 → 静态 → 仿真 → SBOM → 报告全流程，2024 起集成 Binwalk v3 与 unblob |

同时，套件唯一原创、别人没有的资产 —— 003 的 agent 系统层靶场（ATLAS 映射、容器逃逸、
MCP、供应链、web3 场景）—— 投入不足。

这不是一个"要不要用开源"的问题，而是**工程投入往哪放**的问题。本 ADR 要给出一条
可复用的判断规则，而不只是对这两个工具各拍一次脑袋。

## 决策目标

1. 停止在已有成熟替代品的领域做低质量重复建设
2. 不因引入外部依赖而损害商业可分发性
3. 保留已经做出来的、真实可用的能力，不为了"用开源"而推倒重来
4. 给后续同类问题一条不需要重新辩论的规则

## 决定

### 1. 判断规则（后续同类决策直接套用）

对每个"自建 vs 封装"问题，按顺序回答三问：

1. **能力差距是不是数量级的？** 是 → 倾向封装；否 → 倾向自建
2. **许可证是否允许我们预期的分发方式？** 宽松（Apache/MIT/BSD）→ 可封装可捆绑；
   copyleft（GPL/AGPL）→ **只允许互操作，不得捆绑分发**，除非法务另有结论
3. **这块能力是不是我们的差异化来源？** 是 → 自建，哪怕暂时更弱；否 → 封装

三问结论冲突时，**第 2 问是硬约束，优先级最高**。

### 2. 005：接入 Ghidra headless 作为可选反编译后端

**依据**：能力差距是数量级的（IR 级反编译 vs 线性伪 C）；Ghidra 是
**Apache 2.0**，允许商业封装与捆绑；反编译不是 005 的差异化来源 —— 差异化在其上的
LLM 分析层。

**实施约束**：

- 005 **已有**可插拔的加载后端：`backends/base.py` 的 `BinaryBackend` Protocol
  （`supports()` / `load()`）与 `BinaryLoader` 的回退链。但那是**加载**的接缝，
  **反编译没有接缝** —— `decompiler.py` 是直接调用的。因此需要**新建一个
  `DecompilerBackend` 协议**，镜像现有 backend 模式，而不是把 Ghidra 塞进
  `BinaryBackend`
- **保留现有 capstone 伪 C 路径**，作为无 JVM 环境的降级层。不要删 —— Ghidra 需要
  JVM 与数 GB 内存，不是所有部署都有
- 后端选择必须显式可控，且在 Finding 里记录"本次结论来自哪个后端"。不同后端的输出
  质量不同，混在一起而不标注会污染 `010`/`011` 建立的评估基线
- Ghidra 以**外部进程**方式调用（`analyzeHeadless`），不做进程内嵌入

### 3. 006：不捆绑 EMBA，改为互操作 + 自建 SBOM

**依据**：

- **EMBA 是 GPL-3.0-only**。这是与 005 的决定性区别。GPL-3.0 无网络 copyleft
  （那是 AGPL），因此**纯 SaaS 使用不受约束**；但一旦把 EMBA 放进我们分发的镜像或
  安装包，就构成分发 GPL 软件，须承担相应义务
- 006 与 EMBA 的能力差距**不是数量级的**：006 已有真实的 binwalk 封装、真实的
  Docker/QEMU 用户态仿真、CVE 匹配。它是 EMBA 的子集，不是空壳
- 006 的差异化在 LLM 攻击链推理（`attack_chain.py` 走 `MultiAgentOrchestrator`），
  这部分 EMBA 没有

**实施约束**：

- **不得**把 EMBA 打进任何我们分发的镜像、安装包或依赖清单
- 支持**导入 EMBA 报告**：客户自行安装运行 EMBA，006 读取其输出并接管 LLM 分析。
  这条路径完全不涉及分发，规避许可证问题
- ~~**自建 CycloneDX SBOM 输出**~~ —— **2026-08-15 更正：006 已经实现了。**
  `src/ai_firmware_agent/sbom/cyclonedx.py`（226 行）产出 CycloneDX 1.5 JSON，
  EPSS/KEV 以 properties 承载，含 VEX 风格 `vulnerabilities` 数组，并有四个专门的
  测试文件（`test_cyclonedx_bom.py`、`test_sbom_components.py`、`test_sbom_vex.py`、
  `test_cli_sbom_output.py`）。CLI 的 `--sbom` 选项已可用。

  本条源于 2026-08-12 架构审查中"006 缺 SBOM 标准输出"的判断，该判断**是错的** ——
  当时只扫了模块名没有看 CLI 导入。**不得据此派活**，那会重做已有能力。
  这一条同时也削弱了"006 与 EMBA 差距不是数量级"的论据强度：差距比原判断**更小**，
  因此第 3 条"不捆绑 EMBA"的结论不变，理由更充分。
- 若将来商业形态确定为纯 SaaS 且法务确认可行，可重新评估捆绑

### 4. 法律复核是前置条件，不是事后补票

第 3 条中关于 GPL-3.0 的表述是**基于公开许可证文本的工程判断，不是法律意见**。
本 ADR 的作者不具备法律资格。

**接受本 ADR 不等于取得法律结论。** 在任何形式的 EMBA 集成进入分发物之前，必须由
决策层取得独立法律复核。在此之前，只允许第 3 条的"互操作"路径。

### 5. 省下的工程量投向 003

005 停止深化自研反编译、006 停止平行造提取流水线之后释放的工程量，**优先投向 003**
的场景扩充与 CI 化。理由见背景：那是套件唯一不可替代的资产。

本条不设强制比例，但 `013` 及之后的派活排期应体现这一倾斜。

## 未采用方案

| 方案 | 未采用原因 |
|---|---|
| 005 继续自研反编译至可用水平 | 与 Ghidra 的差距是数量级的，追赶成本远超收益，且反编译不是差异化来源 |
| 005 直接删除 capstone 路径、只留 Ghidra | Ghidra 需 JVM 与数 GB 内存；删掉降级层会让轻量部署不可用 |
| 006 捆绑 EMBA 进分发镜像 | GPL-3.0 分发义务；且 006 与 EMBA 差距非数量级，收益不足以抵消法律风险 |
| 006 完全放弃固件流水线、只做 EMBA 报告的 LLM 分析层 | 会丢掉已经可用的 QEMU 仿真能力，且让产品完全依赖客户是否安装 EMBA |
| 用 AGPL 视角处理 EMBA | EMBA 是 GPL-3.0-only，无网络 copyleft 条款，按 AGPL 处理会过度限制 SaaS 形态 |

## 安全与运维影响

- **新增外部进程边界**：Ghidra headless 与 EMBA 报告导入都引入外部输入。二者的输出
  **必须经过 `011` 建立的 `wrap_untrusted` 边界**才能进入 prompt —— 反编译产物和
  第三方报告同样是攻击者可影响的内容
- **部署体积**：接入 Ghidra 的镜像会显著变大（JVM + Ghidra 本体）。应作为可选
  layer，不进默认镜像
- **评估基线**：后端切换会改变 LLM 输入，`010`/`011` 的黄金集需要按后端分别录制，
  否则换后端会误报为质量回归
- **供应链**：新增两个外部工具的版本与来源需进入 `suite-lock.yml` 的记录范围

## 接受条件

1. 决策层确认第 1 条判断规则可作为后续同类决策依据
2. 决策层确认第 3 条的"不捆绑 EMBA"约束，并接受第 4 条的法律复核前置
3. 决策层确认第 5 条的投入倾斜方向

## 解锁规则

本 ADR 被接受后：

- 起草 `013`，覆盖 005 的 `DecompilerBackend` 接缝 + Ghidra 后端 + 后端标注
- 006 的 CycloneDX SBOM 与 EMBA 报告导入可并入 `013` 或另开阶段
- 在此之前，**任何触及 005 反编译深化或 006 提取流水线的派活一律不发**
  （`012-STRUCT-DEBT.md` §6 已据此排除相关工作）
