### Security and deployment status

#### Leaked E2E token — three separate facts, do not conflate them

The previously hardcoded `igw_`-prefixed gateway token (originally in
`web-ui` commit `e40fca7`, `tests/e2e/global-setup.ts:26`) has three independent
statuses. Clearing one does not clear the others.

1. **Reachable history — VERIFIED CLEAN (2026-08-06).** A full scan of
   `git rev-list --all` across `web-ui` returned zero matches, as did the same scan
   over `000shared-llm-core` and `000shared-integration`. No branch-reachable commit
   in the suite contains the token.
2. **Local object store — NOT CLEARED (as of 2026-08-06).** The token still exists in
   `web-ui` in orphaned commit `e40fca7`. That commit is unreachable from every ref,
   but it remains reachable through the reflog and is still listed by `git fsck`.
   Under default gc policy the reflog entry expires after 90 days and the unreachable
   object after 30. Until `git reflog expire --expire-unreachable=now --all` followed by
   `git gc --prune=now` is run, anyone with filesystem access to this checkout can
   recover the value with a single `git log -g`.
3. **Credential — NOT ROTATED (as of 2026-08-06).** The token was valid and was exposed.
   It must be revoked and reissued at the IntegrationGateway. **History cleanup is not
   revocation:** items 1 and 2 change who can read the string, not whether the string
   still authenticates. Rotation is the only action that closes this, and it is required
   regardless of the outcome of items 1 and 2.

Propagation note (verified): unreachable objects are not transferred by `git push`, so
the first push of `web-ui` will not carry `e40fca7` to the remote — provided it is an
ordinary branch push and not `git push --mirror` / `--all` over an object-complete copy.
