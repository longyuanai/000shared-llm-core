### Security and deployment status

#### Leaked E2E token — three separate facts, do not conflate them

The previously hardcoded `igw_`-prefixed gateway token (originally in
`web-ui` commit `e40fca7`, `tests/e2e/global-setup.ts:26`) has three independent
statuses. Clearing one does not clear the others.

1. **Reachable history — VERIFIED CLEAN (2026-08-06).** A full scan of
   `git rev-list --all` across `web-ui` returned zero matches, as did the same scan
   over `000shared-llm-core` and `000shared-integration`. No branch-reachable commit
   in the suite contains the token.
2. **Local object store — CLEARED (2026-08-06).** Orphaned commit `e40fca7` had survived
   the branch rewrite: unreachable from every ref, but still reflog-reachable and still
   listed by `git fsck`, and therefore recoverable with a single `git log -g` by anyone
   with filesystem access to the checkout. It was removed with
   `git reflog expire --expire=now --expire-unreachable=now --all` followed by
   `git gc --prune=now --aggressive`.

   Pre-flight before the prune: all four orphaned commits (`0737d1c`, `469cd99`,
   `b3c2d35`, `e40fca7`) were tree-diffed against `HEAD`. The only path present in them
   and absent from `HEAD` was `tests/e2e/global-setup.ts` — the file this milestone
   deliberately deleted — so the prune discarded no unmerged work.

   Post-conditions verified: `git cat-file -t e40fca7` → `fatal: Not a valid object name`;
   `git fsck --unreachable --dangling` → empty; token scan across
   `git rev-list --all --reflog` → zero matches; `git status` clean; branch still six
   commits with `HEAD` unchanged at `3f814af`, so the `suite-lock.yml` web_ui pin
   remains valid.
3. **Credential — ACTIVE LOCAL KEYS REVOKED (2026-08-07).** An independent read-only
   query of the persistent IntegrationGateway Postgres store found two active, unrevoked
   `local-dev` admin keys. Port 3100 had no Dashboard listener. Both keys were revoked
   through `shared-integration-admin api-key-revoke` with actor
   `codex-m2.1-rotation`; a post-change database query returned `revoked=true` for both,
   and `audit_events` contains two matching `api_key.revoked` / `success` records.

   The original plaintext token was deliberately not recovered after the Git object prune,
   so an exact plaintext-to-row mapping was not re-established. Revoking every active key in
   the audited persistent `local-dev` store closes the live credential path in that store;
   it is not evidence about an unexamined backup or a different external Gateway. No
   replacement key was issued because there was no current consumer. The next authorized
   local live E2E run must issue a new short-lived key and remove it after the run.

   **History cleanup is not revocation:** items 1 and 2 removed recoverable copies of the
   string, while item 3 changed authentication state. All three controls were required.

Propagation note: with item 2 complete the object no longer exists locally, so the first
push of `web-ui` cannot carry it to the remote by any push mode. This was already true
for an ordinary branch push before the prune (unreachable objects are not transferred);
the prune additionally closes the `git push --mirror` / `--all` case and removes the
local-filesystem recovery path.

**Confirmed after publication (2026-08-06).** `web-ui` has since been pushed, and the
remote was checked against the propagation claim above:

- `repos/longyuanai/web-ui/commits` → exactly 6 commits, identical to the local branch.
- `repos/longyuanai/web-ui/commits/e40fca7…` → HTTP 422, "No commit found for SHA".
- `repos/longyuanai/web-ui/contents/tests/e2e` → `dashboard.spec.ts` and
  `live-dashboard.spec.ts` only; `global-setup.ts` is absent.

These checks confirm that the leaked commit and file did not reach the published GitHub
repository: `web-ui` had no remote configured while the leak existed, and its first
publication happened after the prune. This conclusion is limited to the GitHub repository
and the explicitly scanned working tree, Git object store, and generated test artifacts; it
does not claim that every external backup, terminal capture, or process log was audited.

- Production `GATEWAY_URL` and production Gateway credentials remain external deployment

- **Publication status (superseded — this section originally read "no push was
  performed").** `web-ui` was published on 2026-08-06 to `longyuanai/web-ui`, created
  **private**, with `main` at `3f814af` — matching the `suite-lock.yml` web_ui pin, so no
  lock update was required. It is the ninth and last locked repository to reach GitHub;
  the other eight are public. `000shared-llm-core` was subsequently pushed and now carries
  the nine-repository checkout and lock-validation workflow.
- **`SUITE_READ_TOKEN` is now a hard dependency of `inspect.yml`.** Before `web-ui` existed
  the workflow's `secrets.SUITE_READ_TOKEN || github.token` fallback always resolved to
  `github.token`, and it worked only because all seven checked-out repositories were
  public. `web-ui` is private, so cross-repository checkout of it cannot fall back —
  the secret must be present or the "Check out web UI" step fails with a 401.
  The secret was configured on `longyuanai/000shared-llm-core` on 2026-08-06 using a
  fine-grained token scoped to `web-ui` only with `Contents: Read-only`, issued **with no
  expiration**. Rationale and residual risk: a non-expiring credential cannot silently
  break CI later, and the fine-grained scope keeps the blast radius to read-only access to
  one private repository. The accepted trade-off is that nothing forces a periodic review,
  so this token must be rotated manually. It has no automatic review date.
